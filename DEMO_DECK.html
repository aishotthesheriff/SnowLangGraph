Act 2 · The design decision

The planner is not an LLM — on purpose

Deterministic routing (Python)

  • Matches question terms to agents (word starts: api matches “APIs”, not “rapid”)
  • Same question → same route, every time
  • Zero tokens spent on routing
  • Covered by an offline unit-test suite — no Snowflake login needed
  • Misses fall back to the analyst and are tagged planner_fallback

LLM only where it earns its cost

  • Cortex Analyst turns English into SQL over governed Semantic Views
  • The trial account blocks AI_COMPLETE, Cortex Search and the Agent :run endpoint
  • Cortex Analyst REST + SEMANTIC_VIEW(...) SQL run natively on trial
"I chose that on purpose. This is a Snowflake trial account, and it blocks AI_COMPLETE. So I put the LLM only where it earns its cost — Cortex Analyst turning English into governed SQL — and kept routing deterministic." If asked about questions the rules miss: "Unmatched questions fall back to the data analyst, and the trace is tagged planner_fallback, so I can count misses in LangSmith." Managed Cortex Agents mode is one env flag away, but untested on this trial — say so.

Act 3 · Why this matters

The database stops being a black box

-- every SQL statement the agent runs carries
QUERY_TAG = {
  "app":      "snowlanggraph",
  "trace_id": "<LangSmith trace id>",
  "agent":    "RESEARCH_AGENT",
  "step":     3,
  "tool":     "CORTEX_ANALYST_SQL"
}
-- and every LangSmith SQL span carries
snowflake_query_id = <sfqid>
  • LangSmith → Snowflake: each SQL span holds the Snowflake query ID
  • Snowflake → LangSmith: each query is tagged with the trace ID, read through AGENT_OBSERVABILITY_LOGS
  • The tag is sent per statement, so concurrent users on one shared session never mix tags
  • A platform team can check SQL time and rows per agent step from inside Snowflake — no LangSmith access needed
Text-to-SQL time lives on the LangSmith side. The Cortex Analyst REST call itself is not tagged — only the SQL it produces.
"Most agent demos stop on the left. You see node timings, and the database is a black box. On the right is Snowflake's own query history for the same run." Be honest about the boundary: the Analyst REST call is not in query history; the SQL it generates is.

Act 4 · The CLV story

The model refused to guess — and that was right

Before

“What is the average customer lifetime value by industry?”

Cortex Analyst: customer lifetime value is not defined in the semantic model, and there are several valid ways to calculate it. Which one do you mean?

No SQL written. Showed up as the 1 miss in 12 eval runs — treated as a finding, not hidden.

After

Defined once, in both Semantic Views:

CUSTOMER_LIFETIME_VALUE =
  final_monthly_revenue
  × days_since_signup / 30
  -- realized CLV, churned customers

media ≈ $6,782 · manufacturing ≈ $6,730 · technology ≈ $5,034

The LLM translates English into SQL — but only over metrics, joins and synonyms the business has defined. The definition lives under Snowflake governance, not in a prompt.
Live cue (optional): ask "What is the average customer lifetime value by industry?" in a new Studio thread and point at the interpretation line. "A model that guesses a business formula gives you a confident number nobody can audit." If asked whether it's a good CLV formula: "It is a realized value for customers who already left, so it understates active customers. A predictive CLV is the next step — a change in one place."
